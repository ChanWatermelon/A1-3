# AI 코딩 도구 사용 기록

| 항목 | 내용 |
| --- | --- |
| 사용 도구 | Claude Code (VS Code 확장) |
| 작업일 | 2026-08-14 |
| 대상 | 몰입 설계소 웹 서비스 전체 구현 |

이 문서는 "AI에게 코드를 받았다"가 아니라 **어떤 순서로 지시했고, 무엇이 잘못됐으며,
원인을 어떻게 파악해 고쳤는지**를 기록한 것입니다.

---

## 1. 진행 순서

| 단계 | 지시한 내용 | 산출물 |
| --- | --- | --- |
| 1 | 기존 과제(a1-1, a1-2) 구조를 확인해 문서 스타일과 오류 처리 방식을 맞출 것 | 스타일 기준 확정 |
| 2 | 예시(멍냥케어)와 겹치지 않는 아이디어 정의 — 타겟/문제/AI 기능 | 서비스 기획 |
| 3 | 프로젝트 뼈대 생성 (`index.html`, `css/`, `js/`, `api/`, `requirements.txt`, `vercel.json`) | 폴더 구조 |
| 4 | 5개 섹션 + 반응형 + 다크 모드로 프론트 구현 | HTML/CSS |
| 5 | 입력 검증 → fetch → 결과 렌더링 + 오류 코드별 안내 | `js/routine.js` |
| 6 | Python 서버리스 함수로 AI 호출, 응답 검증·정규화 | `api/routine.py` |
| 7 | 로컬 검증 (단위 테스트 + HTTP 테스트 + 화면 캡처) | 테스트 통과 |
| 8 | 문서화 (README, 기획서, 테스트 시나리오) | `docs/` |

## 2. 설계 판단은 직접 내린 부분

AI에게 그대로 맡기지 않고 **먼저 결정한 뒤 지시한** 항목들입니다.

| 결정 | 이유 |
| --- | --- |
| **시각 계산을 AI가 아닌 서버가 한다** | LLM이 시각 덧셈을 자주 틀리고, 총 시간 초과를 코드로 막을 수 없기 때문 |
| 서버 타임아웃(20초) < 브라우저 타임아웃(25초) | 서버가 먼저 포기해야 원인이 담긴 오류 메시지를 사용자에게 전달할 수 있음 |
| 오류 코드를 문자열로 정의하고 화면 문구는 프론트가 소유 | 서버가 만든 기술 문구를 그대로 노출하면 사용자에게 도움이 안 되고, 응답 원문에 키가 섞일 위험도 있음 |
| 입력 시간을 select로 제한 | 자유 입력을 허용하면 비정상 값 검증 부담이 커짐 |
| 외부 라이브러리·CDN 0개 | 과제 조건(바닐라)과 로딩 속도, 그리고 의존성 없는 배포 |

## 3. AI가 만든 코드를 그대로 쓰지 않고 고친 부분

| 항목 | 처음 생성된 코드 | 수정한 내용과 이유 |
| --- | --- | --- |
| 타임아웃 감지 | `controller.abort('timeout')` 후 `signal.reason` 으로 판별 | `AbortSignal.reason` 은 구형 브라우저에 없어 타임아웃을 놓칠 수 있음 → `timedOut` 플래그 변수로 변경 |
| 오류 메시지 | 서버 메시지를 항상 화면에 그대로 표시 | 제목과 본문이 같은 문장으로 중복됨 → 아는 오류 코드는 프론트의 안내 문구(다음 행동 포함)를 쓰고, 모르는 코드일 때만 서버 메시지 사용 |
| 한국어 줄바꿈 | 기본 `word-break` | 모바일에서 "함께"가 "함 / 께"로 끊김 → `word-break: keep-all` + `overflow-wrap: break-word` 적용 |
| 마지막 블록 | AI가 휴식으로 끝내는 경우가 있음 | 마무리가 휴식이면 어색하므로 서버에서 후행 휴식 블록 제거 |

## 4. 발생한 오류와 원인 파악 과정 (핵심)

### 사례 1. 로컬 개발 서버에서 POST 요청이 전부 끊김

**증상**
GET(`/api/health`)은 정상인데 모든 POST 요청이 `The underlying connection was closed` 로 실패.

**원인 파악**
서버 로그를 확인하니 예외가 찍혀 있었습니다.

```
AttributeError: 'DevHandler' object has no attribute '_send'
```

처음 작성한 개발 서버는 `api/routine.py` 의 `handler.do_POST` **메서드 하나만** 떼어
개발 서버 인스턴스에 붙여 실행했습니다. 그런데 `do_POST` 내부에서 `self._send(...)`,
`self._client_ip()` 같은 **같은 클래스의 다른 메서드**를 호출하는데, 그 메서드들은 옮겨오지 않아
`AttributeError` 가 난 것입니다. GET은 예외 경로를 타지 않아 우연히 성공했습니다.

**수정**
메서드 하나가 아니라 **클래스 전체를 합쳐서** 요청 처리 순간에만 인스턴스의 클래스를 바꿔 끼우도록
변경했습니다. (상태는 모두 인스턴스에 있어 안전)

```python
combined = type("Dev_...", (api_handler_cls, dev_cls), {})
self.__class__ = combined   # 처리 중에만 교체
...
self.__class__ = original   # 끝나면 되돌림
```

**배운 점**: "일부만 옮겨 붙이기"는 그 코드가 자기 클래스의 다른 멤버에 의존하는 순간 깨집니다.
그리고 이 문제는 **배포 환경에서는 발생하지 않습니다** — Vercel은 클래스 전체를 그대로 쓰기 때문입니다.
로컬 전용 도구가 만든 문제였고, 이것이 곧 "로컬과 배포 환경의 차이"의 실례입니다.

### 사례 2. 모바일 레이아웃이 깨진 것처럼 보였던 문제

**증상**
헤드리스 브라우저를 390px 폭으로 실행해 캡처했더니, 글자가 오른쪽에서 잘리고
헤더의 다크 모드·햄버거 버튼이 화면 밖으로 밀려나 있었습니다. CSS 반응형 버그로 보였습니다.

**원인 파악 (성급한 수정을 하지 않은 이유)**
CSS를 바로 고치기 전에 **실제로 넘치는 요소가 무엇인지** 측정하는 진단 페이지를 만들었습니다.
페이지 안에서 모든 요소의 `getBoundingClientRect()` 를 검사해 뷰포트 밖으로 나간 것을 출력하게 했더니,
첫 줄에 이렇게 찍혔습니다.

```
viewport=512  scrollWidth=512  body.scrollWidth=512
```

**요청한 창 폭은 390px인데 실제 뷰포트는 512px** 이었습니다.
Windows용 Chrome이 창 최소 폭을 강제해서, 512px로 렌더링한 화면을 390px로 **잘라서** 저장한 것이었습니다.
즉 CSS 문제가 아니라 **측정 도구의 문제**였습니다.

**수정**
페이지를 `width: 390px` 짜리 iframe 안에서 열어 진짜 390px 뷰포트를 만든 뒤 다시 측정했습니다.

```
iframe viewport=390
scrollWidth=390
OK: 가로로 넘치는 요소 없음
navToggle right=374 (viewport 390)
```

가로 넘침은 없었고 햄버거 버튼도 화면 안에 있었습니다. **CSS는 고칠 필요가 없었습니다.**

**배운 점**: 증상만 보고 고쳤다면 `overflow-x: hidden` 같은 불필요한 코드를 넣어
진짜 문제를 덮었을 것입니다. 고치기 전에 **숫자로 확인**하는 편이 빠릅니다.

### 사례 3. 스크린샷이 전부 빈 화면으로 나옴

**증상** AI 결과 화면을 캡처했는데 배경색만 있는 빈 이미지가 나왔습니다.

**원인** 스크롤 등장 애니메이션(`.reveal { opacity: 0 }`)이 `IntersectionObserver` 로 해제되는데,
헤드리스 브라우저의 가상 시간 환경에서는 관찰 콜백이 실행되지 않아 모든 요소가 투명한 상태로 남았습니다.

**수정** 캡처용 페이지에서만 애니메이션을 끄는 스타일을 주입해 해결했습니다.
(운영 코드는 건드리지 않았습니다. 실제 브라우저에서는 정상 동작합니다.)

## 5. 검증에 사용한 방법

AI가 만든 코드를 신뢰하지 않고 아래 3단계로 확인했습니다.

| 단계 | 방법 | 확인한 것 |
| --- | --- | --- |
| 1. 단위 검증 | `validate` / `extract_json` / `normalize` 등을 직접 호출하는 테스트 스크립트 | 빈 입력·경계값·자정 넘김·총 시간 초과 처리 |
| 2. 통신 검증 | `requests.post` 를 가짜 응답으로 바꿔 OpenAI/Gemini 경로 실행 | 헤더 위치, **키가 URL·본문에 새지 않는지**, 오류 코드 매핑 |
| 3. 화면 검증 | 로컬 서버 + 헤드리스 브라우저 캡처 | 데스크톱/모바일 레이아웃, 성공·오류·지연 화면, 다크 모드 |

특히 2단계에서 **"요청 URL과 본문 어디에도 키 문자열이 포함되지 않는다"** 를 자동으로 확인하게 만들었습니다.
키는 헤더로만 나가야 하며, URL에 들어가면 로그·리퍼러를 통해 유출될 수 있기 때문입니다.

## 6. 이 과정에서 스스로 설명할 수 있게 된 것

1. **HTML/CSS/JS의 역할 분담** — 구조(무엇이 있는가) / 표현(어떻게 보이는가) / 동작(무엇이 일어나는가)
2. **입력 → fetch → 응답 → DOM 반영의 흐름** — `preventDefault()` 로 새로고침을 막고,
   `JSON.stringify` 로 본문을 만들고, `await response.json()` 결과로 `createElement` 하는 순서
3. **서버리스 함수의 구조** — `api/*.py` 파일 하나가 곧 엔드포인트이고, `handler` 클래스가 진입점이며,
   요청마다 실행되고 사라지므로 메모리에 상태를 오래 둘 수 없다는 점
4. **환경 변수로 키를 관리하는 이유** — 브라우저 코드에 키를 넣으면 개발자 도구에서 그대로 보이고,
   GitHub에 올리면 즉시 수집된다. 서버가 대신 들고 호출하는 프록시 구조가 필요하다
5. **로컬과 배포의 차이** — 실행 주체, 환경 변수 주입 방식, 시간대(UTC vs KST), 반영 시점이 다르며,
   그래서 `/api/health` 같은 점검용 엔드포인트가 디버깅에 유용하다
6. **오류를 읽는 순서** — 증상 → 서버 로그의 예외 → 예외가 난 줄의 전제 확인 → 도구 자체를 의심
