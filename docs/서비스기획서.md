## 1. 기획 배경

### 1-1. 문제 정의

할 일 관리 도구는 이미 많습니다. 그런데도 일이 시작되지 않는 이유는 **목록이 계획이 아니기 때문**입니다.

- 목록은 "무엇을"만 알려 주고 **"언제, 얼마나, 어디까지"**를 알려 주지 않습니다.
- 남은 시간에 무엇을 넣을지 고르는 것 자체가 의사결정 비용이고, 이 비용이 착수를 늦춥니다.
- 컨디션이 나쁜 날에도 평소와 같은 계획을 세워 두면, 실패한 계획이 되고 자책으로 이어집니다.
- 휴식을 계획에 넣지 않으면 후반부에 집중력이 급락합니다.

### 1-2. 왜 AI가 필요한가

"3시간에 논문 서론 초안과 실험 데이터 정리를 어떤 순서로 배치할 것인가"는
**규칙 기반으로 풀기 어려운 문제**입니다. 작업의 인지 부하, 컨디션, 남은 시간의 조합이 매번 다르고,
사용자가 자유 문장으로 적은 할 일을 이해해야 하기 때문입니다.
정해진 템플릿(예: 무조건 뽀모도로 25분)을 돌려주는 것으로는 "내 상황에 맞는 계획"이 되지 않습니다.

### 1-3. 기존 방식과의 차이

| | 일반 To-do 앱 | 뽀모도로 타이머 | **몰입 설계소** |
| --- | --- | --- | --- |
| 순서 결정 | 사용자가 함 | 해당 없음 | **AI가 제안** |
| 시간 배치 | 없음 | 고정 25/5분 | **컨디션에 따라 가변** |
| 완료 기준 | 없음 | 없음 | **블록마다 제시** |
| 휴식 | 없음 | 고정 | **총 시간에 맞춰 배치** |

## 2. 서비스 개요

### 2-1. 목적

사용자가 "지금부터 남은 시간"을 **의사결정 없이 바로 시작할 수 있는 상태**로 만들어 주는 것.

### 2-2. 타겟 사용자

| 구분 | 주 타겟 | 부 타겟 |
| --- | --- | --- |
| 대상 | 마감이 있는 대학원생·연구원 | 재택/자율 근무 지식노동자 |
| 상황 | 실험·논문·발표가 동시에 굴러가고 우선순위가 매일 바뀜 | 회의 사이의 비는 시간을 흘려보냄 |
| 필요 | "지금 3시간에 뭐부터 할지" 즉답 | 짧은 시간의 밀도 있는 사용 |
| 사용 시점 | 하루 중 작업 시작 직전 (오전 10시 / 오후 2시경) | 회의 종료 직후 |

**대표 사용자 시나리오**
> 박사과정 2년차 A는 오후 2시에 자리에 앉았다. 저녁 6시 세미나 전까지 4시간이 있고,
> 학회 슬라이드 초안과 3차 실험 데이터 정리를 해야 한다. 어제 늦게 자서 컨디션은 보통 이하다.
> A는 몰입 설계소에 세 가지를 입력하고, **몇 시에 무엇을 어디까지 할지 적힌 시간표**를 받아
> 고민 없이 첫 블록을 시작한다.

### 2-3. 제공 가치

1. **결정 대행** — 순서와 시간 배분을 대신 정해 준다.
2. **완료 기준** — 블록마다 "이만큼 하면 성공"을 제시해 막연함을 없앤다.
3. **회복 설계** — 휴식을 계획의 일부로 넣어 후반부 급락을 막는다.
4. **즉시성** — 회원가입·설치 없이 10초 안에 결과를 받는다.

### 2-4. 하지 않는 것 (범위 제외)

- 캘린더 연동, 알림/타이머 실행, 계정·로그인, 팀 공유
- 서버에 사용자 입력을 저장하는 기능 (개인정보 최소화 원칙)

## 3. 페이지 / 섹션 구성

한 페이지 안에서 상단 메뉴로 이동하는 **5개 섹션** 구조입니다.
(모바일에서는 햄버거 버튼 → 펼침 메뉴, 클릭 시 자동으로 닫힘)

| # | 섹션명 | 앵커 | 목적 | 주요 구성 요소 |
| --- | --- | --- | --- | --- |
| 1 | 홈 | `#home` | 3초 안에 무엇을 해 주는 서비스인지 전달 | 헤드라인, CTA 2개, 결과 미리보기 카드, 신뢰 배지 |
| 2 | 서비스 소개 | `#about` | 신뢰 확보 + 동작 방식 설명 | 해결 문제 3카드, 동작 방식 4단계 |
| 3 | **AI 몰입 설계** | `#design` | **핵심 기능 수행** | 입력 폼, 결과 타임라인, 최근 기록 |
| 4 | 집중 가이드 | `#tips` | 이탈 방지 + 사용법 안내 | FAQ 5개(아코디언), 집중 팁 3개 |
| 5 | 문의하기 | `#contact` | 피드백 수집 | 문의 폼(이름/이메일/유형/내용) |

**이동 방식**: 헤더 고정 메뉴(앵커 링크) + 스크롤 위치에 따라 현재 섹션 메뉴가 강조됩니다(IntersectionObserver).
푸터에도 동일한 메뉴를 배치했습니다.

**화면 크기별 대응**

| --- | --- | --- |
| 데스크톱 | 1025px+ | 히어로 2단 / 카드 3열 / 설계 화면 좌우 2단 |
| 태블릿 | 761~1024px | 히어로 1단 / 카드 2열 / 설계 화면 상하 2단 |
| 모바일 | ~760px | 전체 1열 / 햄버거 메뉴 / 버튼 전체 폭 |

## 4. 핵심 기능 정의

### 4-1. 기능 목록

| 우선순위 | 기능 | 설명 |
| --- | --- | --- |
| P0 | **AI 몰입 루틴 설계** | 입력값으로 시간 블록 타임테이블 생성 |
| P0 | 실패 처리 안내 | 빈 입력 / API 오류 / 지연 상황별 안내 문구 |
| P1 | 결과 텍스트 복사 | 메모 앱·슬랙에 붙여넣기 |
| P1 | 최근 설계 기록 | 브라우저 로컬에 최근 3건 저장 |
| P1 | 다크 모드 | 야간 작업 환경 대응, 선택 기억 |
| P2 | 문의 접수 | 웹훅 연동 시 외부 도구로 전달 |
| P2 | 상태 점검 API | `/api/health` 로 배포 환경 확인 |

### 4-2. AI 기능 상세 설계

#### 입력 (Input)

| 항목 | UI | 필수 | 제약 | 이유 |
| --- | --- | --- | --- | --- |
| 오늘 할 일 | textarea | **필수** | 5~300자 | 계획의 재료. 너무 짧으면 이해 불가, 너무 길면 토큰 낭비 |
| 사용할 수 있는 시간 | select | 필수 | 60/90/120/180/240/360분 | 자유 입력을 막아 비정상 값 차단 |
| 시작 시각 | time | 선택 | HH:MM | 비우면 현재 시각(KST)으로 계산 |
| 컨디션 | range 1~5 | 필수 | 정수 | 블록 길이·휴식 빈도 결정 |
| 작업 유형 | radio 6종 | 필수 | — | 작업 성격에 맞는 요령 제시 |
| 방해 요소 | text | 선택 | 100자 | 개인화된 대처법 제시 |

#### 출력 (Output)

| 필드 | 형식 | 설명 |
| --- | --- | --- |
| `headline` | 문자열 | 오늘 설계의 한 줄 요약 |
| `strategy` | 문자열 | 이 순서로 배치한 이유(2문장) |
| `blocks[]` | 배열 | `type`(focus/break), `title`, `goal`(완료 기준), `tip`, `duration_min`, `start`, `end` |
| `checklist[]` | 배열 | 마무리 확인 항목 3개 |
| `caution` | 문자열 | 오늘 주의할 점 |

**화면 표현**: 세로 타임라인 카드. 집중 블록은 보라색 점, 회복 블록은 초록 배경으로 구분하고,
각 카드에 `시작–종료 시각`, `집중/회복 배지`, `소요 시간`, `완료 기준`, `요령`을 표시합니다.

#### 시간 계산 원칙 (설계상 핵심 결정)

> **AI에게는 각 블록의 "소요 분(duration_min)"만 요구하고, 실제 시각은 서버가 계산합니다.**

- 이유 1: LLM은 시각 덧셈을 자주 틀립니다. (14:00 + 45분 = 14:55 같은 오류)
- 이유 2: 서버가 누적 계산하면 **총 시간이 사용자 입력을 초과할 수 없음**을 코드로 보장할 수 있습니다.
- 처리: 누적 합이 총 시간을 넘으면 해당 블록을 남은 시간만큼 줄이고, 이후 블록은 버립니다.
  마지막이 휴식으로 끝나면 제거합니다.

#### 프롬프트 설계 요약

- **system**: "집중 시간 설계 코치. 설명 없이 JSON 객체 하나만 출력."
- **user**: 조건(할 일/시간/시작 시각/컨디션/유형/방해 요소) + 설계 규칙 8개 + 출력 스키마
- 주요 규칙: 컨디션별 블록 길이(높음 45~50분 / 보통 35~40분 / 낮음 20~25분),
  집중 사이 휴식 5~15분, 인지 부하 높은 작업 앞 배치, 마지막 블록은 '다음 작업 예약',
  **사용자가 적지 않은 할 일을 지어내지 말 것**
- JSON 강제: OpenAI `response_format: json_object` / Gemini `responseMimeType: application/json`

## 5. AI 기능 실패 처리 기준

### 5-1. 단계별 차단 지점

```
[1단계] 브라우저 검증   빈 입력 · 5자 미만 → 네트워크 요청 없이 즉시 차단
[2단계] 서버 검증       본문 크기 · 필수값 · 값 범위 → 400 응답
[3단계] 호출 빈도 제한   같은 IP 1분 8회 초과 → 429 응답 (과금 보호)
[4단계] AI 호출         인증·한도·서버 오류·타임아웃 → 코드별 매핑
[5단계] 응답 검증       JSON 파싱 실패 · 블록 없음 → 502 PARSE_ERROR
```

### 5-2. 오류별 처리 기준표

| 상황 | 판정 기준 | HTTP | 코드 | 사용자 안내 | 다음 행동 버튼 |
| --- | --- | --- | --- | --- | --- |
| 빈 입력 | 공백 제거 후 길이 0 | 400 | `EMPTY_INPUT` | "할 일을 입력해 주세요" | 입력 수정하기 |
| 너무 짧음 | 5자 미만 | 400 | `TOO_SHORT` | "조금만 더 적어 주세요" | 입력 수정하기 |
| 너무 김 | 300자 초과 | 400 | `TOO_LONG` | "입력이 너무 깁니다" | 입력 수정하기 |
| 값 오류 | 허용 목록 밖 | 400 | `INVALID_INPUT` | "입력값을 확인해 주세요" | 입력 수정하기 |
| 연타 | 1분에 8회 초과 | 429 | `RATE_LIMITED` | "잠시 후 다시 시도해 주세요" | 다시 시도 |
| 키 미설정 | 환경 변수 없음 | 500 | `NO_API_KEY` | "AI 기능이 아직 설정되지 않았습니다" | 다시 시도 |
| 인증 실패 | AI가 401/403 | 502 | `UPSTREAM_AUTH` | "AI 서비스 인증에 실패했습니다" | 다시 시도 |
| 한도 초과 | AI가 429 | 429 | `UPSTREAM_QUOTA` | "AI 사용량 한도를 초과했습니다" | 다시 시도 |
| AI 서버 오류 | AI가 5xx | 502 | `UPSTREAM_ERROR` | "AI 서비스가 불안정합니다" | 다시 시도 |
| 형식 오류 | JSON 파싱 실패 | 502 | `PARSE_ERROR` | "결과를 이해하지 못했습니다" | 다시 시도 |
| **서버 지연** | AI 응답 20초 초과 | 504 | `TIMEOUT` | "응답이 너무 늦습니다" | 다시 시도 |
| **브라우저 지연** | 25초 초과 | — | `TIMEOUT` | "응답이 너무 늦습니다" | 다시 시도 |
| 네트워크 끊김 | fetch 실패 | — | `NETWORK` | "네트워크에 연결할 수 없습니다" | 다시 시도 |

### 5-3. 지연(Latency) UX 규칙

| 경과 시간 | 동작 |
| --- | --- |
| 0초 | 버튼 비활성화 + 스피너, 결과 영역을 로딩 상태로 전환 |
| 0~8초 | "보통 5~10초 정도 걸립니다" |
| 8초 이후 | "조금 더 걸리고 있습니다. 잠시만 기다려 주세요…" |
| 20초 | (서버) AI 호출 포기 → 504 반환 |
| 25초 | (브라우저) AbortController로 요청 중단 → 안내 표시 |

**타임아웃 순서를 서버(20초) < 브라우저(25초)로 둔 이유**: 서버가 먼저 포기해야
사용자가 "왜 실패했는지"를 담은 서버 메시지를 받을 수 있습니다. 반대 순서면 원인 불명으로 끊깁니다.

### 5-4. 오류 메시지 작성 원칙

1. 원인을 사용자 언어로 쓴다. (`UPSTREAM_QUOTA` ✗ → "사용량 한도를 초과했습니다" ○)
2. 다음에 할 행동을 붙인다. ("잠시 후 다시 시도해 주세요")
3. 사용자가 고칠 수 있는 오류와 그렇지 않은 오류의 버튼을 다르게 한다.
4. **기술적 세부 정보나 API 응답 원문을 화면에 노출하지 않는다.** (키 유출 위험) 서버 로그에만 남긴다.

## 6. 보안 및 운영 기준

| 항목 | 기준 |
| --- | --- |
| API 키 관리 | 코드·문서·화면 어디에도 값을 두지 않고 환경 변수로만 주입 |
| 키 노출 차단 | 프론트는 `/api/...` 만 호출. 브라우저는 키를 알 수 없음 |
| 오류 로그 | AI 응답 본문은 서버 로그(최대 300자)에만, 화면에는 미노출 |
| 개인정보 | 입력값을 서버에 저장하지 않음. 최근 기록은 브라우저 localStorage |
| 과금 보호 | 요청 본문 8KB 제한, 입력 300자 제한, IP당 1분 8회 제한 |
| 상태 점검 | `/api/health` 는 키의 **설정 여부(true/false)만** 반환 |

## 7. 성공 기준 (측정 방법 포함)

| 지표 | 목표 | 측정 방법 |
| --- | --- | --- |
| AI 기능 성공률 | 95% 이상 | 전체 요청 대비 `ok: true` 비율 (Vercel 함수 로그) |
| 응답 시간 | 중앙값 10초 이내 | Vercel Functions의 Duration |
| 오류 안내 도달률 | 100% | 모든 실패 경로가 안내 문구로 끝나는지 (테스트 시나리오 12종) |
| 모바일 정상 표시 | 깨짐 0건 | 390px / 768px / 1440px 실측 |
